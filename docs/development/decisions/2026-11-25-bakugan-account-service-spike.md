## Backend choice

Supabase is the selected prototype provider. Its integrated Auth and PostgreSQL access boundary suit the inventory's relational identity/reference requirements and the existing v2 document. Cloudflare Workers/D1 would need separate identity and application API authorization work. A hosted staging project has not been provisioned. Check service cost, auth delivery, recovery, rate limits and operational expectations before public use; the free plan has capacity/inactivity constraints and no automatic backups. Discord OAuth and email OTP are supported candidates for managed sign-in. The default email service is only suitable for restricted testing, not public sign-up. See [Supabase Auth](https://supabase.com/docs/guides/auth), [database functions](https://supabase.com/docs/guides/database/functions), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [pricing](https://supabase.com/pricing), [SMTP](https://supabase.com/docs/guides/auth/auth-smtp), [Discord sign-in](https://supabase.com/docs/guides/auth/social-sign-in/auth-discord), and [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/).

## Implemented database contract

- One private, versioned v2 inventory document per authenticated user, with server-side shape, size, identity, quantity, and membership validation. Server revision and local revision are distinct. Conditional updates lock the owner row; same latest mutation replays, an older retry conflicts instead of overwriting a later save. Empty inventory is a saved revision, not a reset to revision zero.
- Owner identity is obtained from `auth.uid()` only. Private tables are in an unexposed schema, RLS-enabled with neither public nor browser-role table grants. Narrow RPC execution grants and fully schema-qualified definer functions enforce ownership. No browser administrative key is needed.
- Owner previews a Have/Want/Trade snapshot of all or one binder at a saved revision. Creating it requires the same revision and explicit request UUID. The server generates the public projection itself, disclosing only the intended title, item names, kind, ID, set/serial, and selected nonzero quantity. Binder order is retained; private binder name, other quantities and notes never form part of the response.
- Unlisted readers receive a projection only by random publication ID. No anonymous directory or owner metadata is available. Quotas apply to active and daily new publications. Owner revocation removes future reads and clears the projection; links do not track live private edits, and updates are new publications. Owner deletion cascades to the inventory and all publications. Self-service Auth deletion is not yet implemented.

The service repo has embedded PostgreSQL tests using pinned PGlite and a synthetic Supabase role/identity fixture. They execute the actual migration and verify two-owner isolation, anonymous permissions, conditional saves, retries, invalid documents including Unicode bounds, preview/publication projection, revision conflicts, immutable snapshots, revocation, quotas and cascading account-data deletion. This does not verify a real Supabase Auth gateway, public deployment, or simultaneous network connections. A staging-only HTTP smoke script is prepared for two disposable authenticated accounts.

## Frontend and release boundaries

The anonymous `bakugan-suite.inventory.v2` key and legacy migration remain independent of any account. Future sign-in must not silently upload or copy a remote inventory into the guest key. Initially prefer an in-memory signed-in workspace, explicit upload/merge/replace preview, revision-bound saving, clear conflict recovery and account-switch cleanup. Any persistent offline account cache needs its own reviewed isolation model. An unlisted `/baku/shared/?id=…` view will use the same suite theme and noindex but is not yet wired to the main site.

The next prerequisite is a disposable Supabase project with a publishable key (never a secret key), selected sign-in provider and two test accounts. Apply and verify the migration there before using real data. Hosted authentication and account UI, concurrent API requests, private profile switching across archives, self-service export/deletion, rate limits, abuse reporting, and backup/restore operations are launch work. No cloud resource, remote Git repository or paid subscription was created.
