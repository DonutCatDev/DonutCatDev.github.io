# Account workspace and shared-list frontend

Date: 2026-11-26. Status: implemented and locally verified; online configuration disabled by default.

`Bakugan_Collection` release `2026-11-26-account.1` contains the account workspace, API transport and public share reader (pin `82749c0`). The main site assembles `/baku/collection/` and `/baku/shared/` from the one checksum-verified release. The reader subtree is copied only to its canonical sibling route. Both pages use the same Card Archive stylesheet; the shared route is noindex and omitted from the sitemap. No extra frontend repository or backend files are included in the Pages artifact.

## Account isolation and sync behavior

- The guest workspace opens first, including on return from Discord. Signed-in sessions are detected without loading or uploading the guest collection. Opening the online workspace separately retrieves its saved inventory. The same local UI edits an in-memory account draft; item edits, binders, bulk edits and import previews are never automatically sent or written to the guest key. Card and Toy Archive ownership controls remain guest-only until a later shared account adapter is ready.
- Copy from guest previews merge or replace and leaves the guest key byte-for-byte unchanged. Sync is an explicit whole-document operation, limits requests, uses a distinct server revision and retains the exact mutation UUID/body after uncertain delivery. Conflicts preserve the draft and allow reviewing the remote version, keeping remote, maximum merge or deliberate overwrite. None automatically retries against a changed revision. Draft export and navigation warning provide a recovery path; no offline account cache is persisted.
- Session changes signaled across tabs, visibility/focus revalidation, account ID epochs and aborts prevent late responses from appearing under another account. Private content is hidden while verifying, and teardown removes the old workspace when identity changes. Worker commit `e9091db` requires a verified `X-Bakugan-Account` assertion for every private data operation and authenticated logout while authorizing solely by the session cookie. A stale tab's request cannot accidentally read/write the newly signed-in account; the assertion is not an owner selector.
- Publishing requires a clean synced revision, explicit quantity type/binder scope and deliberately public title. The server's projected preview appears first. Confirm is separate; uncertain responses retain the publication request ID. Active links may be revoked. Anonymous share reads omit credentials and validate only the public projection; text rendering, archive links, filtering, pagination and downloadable list do not expose private notes or other quantities. Links are immutable, unlisted and noindex. Revocation cannot recall already downloaded content.

## Staging boundary

The release's `data/service-config.json` contains `apiOrigin:null`. No real API request is sent until a deployment-owned, approved HTTPS site subdomain is configured and the release is regenerated. Production origin parsing rejects arbitrary hosts and URL-derived endpoint overrides; same-origin loopback is accepted for local fixtures only. The Worker still requires provisioning a disposable D1 database, Discord application, staging HTTPS hostname and server-side credentials. Follow `Bakugan_Services/docs/staging.md`; real cross-host cookies, OAuth, hosted CPU/quota behavior, rate/budget protections, self-service account deletion/export and abuse reports remain launch gates. No cloud infrastructure or real user data changed.

Local checks covered account state and contract tests, backend SQLite and workerd/D1 integration, and synthetic Chromium workflows exercising guest adoption, uncertain sync and publication receipts, conflict merge, safe shared rendering, revocation and account switching. Guest data is checked unchanged throughout. Real hosted sign-in is not claimed.
